## 一、他要解决的问题

让几个模型对**同一份材料**各自独立产出，**互不可见**，再一次性揭晓、对比、选一版、形成纪要。

与我们现在的「独立模式」只差最后那几步——但差的正是价值所在：独立作答只产生四份答案，**对比和定稿才产生决策**。

---

## 二、三个核心概念

| 概念 | 含义 |
|---|---|
| **议题 topic** | 一次评审的全部状态：材料、成员、阶段、结论 |
| **材料 material** | 冻结的输入：文字 / 附件 / 文件夹（我们只做文字+附件） |
| **评审 review** | 独立产出的容器，按「槽位 slot」记录每个成员那一份 |

**槽位 slot** 是关键抽象：`{ memberId, stage, status, opinion }`，`status` 有
`queued / running / completed / skipped / recoverable / blocked / cancelled`。
"谁交了、谁跳过、谁挂了"全看槽位，不看人。

---

## 三、七个状态（议题级）

```
preparing → reviewing → discussing → conclusion → confirmed → ended
                 ↘ blocked ↗                      （任何时刻）
```

| 状态 | 含义 | 进入条件 |
|---|---|---|
| `preparing` | 冻结材料、落库 | 开议题时 |
| `reviewing` | 各自独立产出（互不可见） | 材料就绪、评审派发成功 |
| `discussing` | 揭晓后开放讨论 | 独立产出全部完成 + 用户点「开始讨论」 |
| `conclusion` | 纪要已生成，等用户定 | 讨论结束 + 纪要完成 |
| `confirmed` | 结论已确认 | 用户点「确认结论」 |
| `ended` | 议题结束 | 用户点「结束」 |
| `blocked` | 出错，要核对 | 评审失败 / 材料失效 |

**内置评审子状态机**（`reviewing` 阶段里）：
`stage` = 独立产出 → 互评 → 作者答复 → 汇总 → 验证分歧 → 待你决定
`status` = preparing / active / awaiting_author / awaiting_verification / awaiting_decision / completed / stale / blocked / cancelled

---

## 四、三种议题类型

| kind | 中文 | 做法 | 我们做不做 |
|---|---|---|---|
| `review` | 评审 | 大家检查**同一份**材料，挑问题 | ✅ |
| `candidates` | 比稿 | 每人独立写**一版**同样的东西 | ✅ |
| `proposals` | 方案比较 | 每人提**一个方案** | ✅ |

三者流程完全相同，**只有提示词和"选稿方式"的可选项不同**。

## 五、五个关键机制（这才是精华）

### 1. 揭晓（reveal）——"互不可见"是怎么实现的

```js
revealed = 所有 stage==='independent' 的槽位 都 completed 或 skipped
```

未揭晓时，后端 `detail()` **主动把候选内容剥掉**再返回：

```js
review = { ...raw, review: { ...raw.review, conclusion: undefined, findings: [],
         responses: [], dispositions: [] },
          slots: slots.map(({ opinion, summary, verification, responses, ...s }) => s) }
```

**不是前端藏起来，是后端根本不给。** 这一点我们必须照做——否则"互不可见"就是假的了。

揭晓时，把每份稿**写成一条房间消息**（作者=该成员），所以用户看到的画面是：候选稿突然一起出现在聊天里。

### 2. 汇总成员（lead）

- 每个议题有一个 `leadMemberId`
- 选稿方式 `chooser`：
  - `user` = **由我并排比较后选择**
  - `synthesizer` = **由汇总成员综合成新一版**
- 只有非 `review` 类型才出现这个选项

### 3. 采用 ≠ 验收

代码里反复强调（`minutesInstruction` / `export`）：

> 用户确认采用的回复**不代表程序确认结束**；**不能把汇总者的建议或多数意见写成全员共识**。

「采用」只记一个 `selectedSlotId`，不改任何结论。

### 4. 纪要的五段式

生成纪要的提示词钉死了结构：

> body 用中文分别列出「**共识**」「**分歧与各方理由**」「**少数意见**」「**未核实事项**」「**建议**」。
> 没有明确记录就写"未形成"或"未记录"。选用的稿件以用户已保存选择为准，不能自行改变。
> 不写 slotId 等内部编号、不写英文字段名。

并且要把**跳过记录、未核实事项**一并写进纪要末尾。

### 5. 三个防翻车设计

| 机制 | 作用 |
|---|---|
| `requestId` + hash 去重 | 同一个请求编号重复提交，返回同一结果；内容变了则报冲突 |
| `expectedRevision` 乐观锁 | 议题被改过就拒绝操作，提示"请刷新" |
| 未知结果不自动重发（UNKNOWN_RESULT） | 有"结果未知"的运行，必须用户明确确认才能结束 |

## 六、我们搬什么、不搬什么

### 搬（核心价值）

- 七状态机 + 揭晓机制 + 槽位模型
- 三种议题类型
- 并排对比 + 采用
- 五段式纪要 + 确认
- 汇总成员

### 砍（我们没有对应物，搬来是空壳）

| 他的东西 | 为什么不搬 |
|---|---|
| 项目 / artifact / 副本 / 指纹 | 我们不碰文件 |
| 作者答复（author） | 我们没有"成果作者"这个概念 |
| 验证分歧 / 待你决定（子阶段） | 依赖评审引擎，第一版不做 |
| 稿件的文件路径 / deliverablePath | 同上 |
| 幂等 requestId / 未知结果确认 | 我们没有长任务和工具调用，出错直接重来 |
| 权限 / 审计 / tombstones | 单机单人 |

### 换（我们的特色）

| 他的 | 我们的 |
|---|---|
| 带回项目（material/task/plan） | **导出/复制结论**，直接粘给 Claude Code / DSH |
| 独立准备（外部 CLI 跑） | 复用我们的 `独立模式`：并发调 API，互不可见 |
| 审议讨论（房间讨论引擎） | 复用我们的 `圆桌模式`：轮流、可见 |

## 七、落到我们的架构

### 数据模型（`data/topics.json`）

```json
{
  "id": "t_xxx",
  "title": "材料首行或用户输入",
  "kind": "review | candidates | proposals",
  "status": "preparing | reviewing | discussing | conclusion | confirmed | ended | blocked",
  "material": { "text": "...", "attachments": [] },
  "memberIds": ["ds", "k27", "qw"],
  "leadMemberId": "ds",
  "chooser": "user | synthesizer",
  "revealedAt": 1690000000000,
  "slots": [
    { "memberId": "ds", "status": "completed", "text": "...", "at": 1690000000000 }
  ],
  "selectedSlotId": null,
  "conclusion": { "text": "...", "at": 1690000000000 },
  "createdAt": 1690000000000,
  "updatedAt": 1690000000000
}
```

### 议题 = 一个特殊房间

- `roomId = "t:<id>"`，消息照样写进 `room.jsonl`
- 复用现有的一切：`openRoom`、SSE 广播、气泡渲染、状态条
- `rooms.json` 里加一条 `{ "t:<id>": { name, members, topic: true } }`

### 接口（4 个）

| 接口 | 作用 |
|---|---|
| `POST /api/topic/open` | 建议题：标题/类型/材料/成员/汇总成员/选稿方式 |
| `POST /api/topic/reveal` | 揭晓：把槽位写成消息，`revealedAt` 落时间 |
| `POST /api/topic/conclude` | 生成五段式纪要（调一次模型） |
| `POST /api/topic/confirm` | 确认结论 / 结束议题 |

独立准备复用现有的 `独立模式` 分支（并发 `speak`），只是把产出写进槽位而不是直接当消息。

### 界面（三屏）

1. **开议题弹窗**——类型三选一、材料输入、成员多选、选稿方式（非评审才显示）、汇总成员
2. **议题房间**——状态条显示 `状态 · 阶段 · N/M 已交稿`；未揭晓时聊天区只有"各自准备中"；揭晓后候选稿逐条出现
3. **并排对比**——全宽面板，每人一列，底部「采用这份」；采用后回到房间

## 八、分四步做（每步可单独验收）

| 步 | 内容 | 验收 |
|---|---|---|
| **P1** | 数据层 + 开议题 + 独立准备 + 揭晓 | 能建议题、三人各交一份、互不可见、点揭晓后一起出现 |

| **P3** | 纪要生成 + 确认 | 能出五段式纪要、能确认/再议/结束 |
| **P4** | 导出复制 | 一键复制 markdown，能直接粘给 agent |

**先做 P1。** 它是闭环的最小版本：没有 P1，后面全是空中楼阁。
